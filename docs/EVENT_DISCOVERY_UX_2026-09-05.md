# 技術イベント画面の操作改善 — 2026-09-05

## 目的・変更範囲

技術イベントを「探す → 比べる → 気になる候補を保存 → 告知・申込ページを確認」の順で使いやすくする。対象は `/meetups` と共通の左メニュー。インターン、X、Google連携、収集元、API利用予算は維持する。今回、新しいイベントの外部収集・有料API呼び出し・自動申し込み・外部公開は行わない。

## デザイン

APPLE-DESIGN.mdを参考に、設定より候補の発見を優先する。大きな見出し領域と常時表示の設定フォームをやめ、「興味・目的を編集」に折りたたむ。暖色の背景、白に近いカード、濃い文字、オレンジの選択状態を採用する。導入済みLucideアイコンを使い、色だけでなく文言・アイコン・選択表示でも区別する。

カードは「発信元・保存 → タイトル → 分野 → 日程・形式 → 一致理由 → 告知ページ」。タイトルは省略しない。概要は2行に抑え、詳細を開くと全文と参加メモが見える。キーボードフォーカス、44px前後の操作領域、画面幅による1列/2列表示、動きを減らす設定に対応する。

左メニューは現在地をaria-currentで示し、連携・設定を分ける。下部の案内を絶対配置から通常のレイアウトへ変更し、ズーム時の重なりを防ぐ。不要な旧ローディング表示のHTMLも除去する。

## 表示条件と興味設定の分離

- 「すべて / あなた向け / 気になる」を切り替える。
- 検索、複数の分野チップ、開催形式を併用する。分野の複数選択はOR、検索・形式・表示区分との組み合わせはAND。
- チップの件数は、現在の検索・形式・表示区分でその分野を選んだ場合の件数。該当なしでは条件解除への導線を出す。
- 一覧のチップ操作は一時的な絞り込みであり、収集アルゴリズムの設定は変更しない。
- 「興味・目的を編集」で保存した条件を、おすすめ順と既存の次回Xイベント検索へ反映する。成功応答後にだけ保存済み条件を更新し、編集中は未保存と表示する。
- 「新しく見つかった順」は収集日時順であり、開催日順ではない。

分野判定と興味の加点処理を画面・サーバーで共有する。英字語の前後を確認し、detail/email内のAI、build内のUI、across内のOSSなどを誤って拾わない。日本語に隣接した「AIエンジニア」や全角英字は認識する。説明可能なキーワード一致であり、意味理解や高度な機械学習ではない。

開催形式は明示的な記載から判定し、オンライン否定を考慮する。現地＋オンラインは別扱いで、判定できない場合は「形式未確認」と表示する。既存の日付抽出は本文内の別の日付を拾う可能性があり、申し込み前に原文を確認する必要がある。告知に名前や話題が含まれることは、実際に交流できることの保証ではない。

## イベントごとの保存と参加メモ

SQLiteの `MeetupPlan` に `url`（主キー）、`saved`、`people`、`talks`、`updatedAt` を保存する。Candidateは本文更新や収集元違いで同じURLの行が増えるため、候補IDではなくURLをキーにして引き継ぐ。一覧も最新の収集行をURL単位でまとめる。先頭60件を取得してから絞り込む制限をなくし、保存済みの対象候補全体を検索可能にする。

`PATCH /api/meetup-plans` は既存の技術イベント候補URLのみを対象とし、部分更新する。ブックマーク変更でメモを消さず、メモ変更でブックマークを解除しない。メモは各1,000文字。異なるOriginの書き込みを拒否し、保存失敗を成功として表示しない。

個別メモは本人の参加目的を整理するためのもの。全体の興味条件・ランキングには自動反映せず、主催者や外部AIにも送信しない。フィルタ切り替え時も編集中のメモは親コンポーネントに保持する。ページ移動・再読み込み後に残るのは保存済みデータのみ。

「気になる」は再収集後の判定変更でも突然消さず残す。これは募集中・未終了の保証ではない。自動抽出では既存の日本／マレーシア／オンラインの地域条件を維持する。

## 確率的フィードランキング（2026-09-06）

### 目的

X/TikTokのように「日々の興味あり・なしで順位が育つ」操作感を、個人用・localhost・SQLiteという前提を崩さずに実現する。大規模サービスのような全利用者の行動グラフや、非公開の推薦モデルは使わない。本人の判定履歴だけを再計算する、説明可能な確率モデルを採用する。

### 数学モデル

判定値 `v` は `-2, -1, 0, +1, +2` とし、報酬を `r = (v + 2) / 4`（0〜1）へ変換する。未指定の過去データは従来どおり興味ありを `+1`、興味なしを `-1` とみなす。

全判定数を `N`、全報酬和を `Σr`、平滑化係数を `α = 8` として、まず本人の全体傾向を求める。

```text
P0 = (Σr + α × 0.5) / (N + α)
P(feature) = (Σr(feature) + α × P0) / (n(feature) + α)
confidence(feature) = n(feature) / (n(feature) + α)
lift(feature) = 2 × (P(feature) - P0)
```

`feature` は情報源または説明可能な固定話題（生成AI、長期インターン、イベント、ハッカソン等）である。候補の最終点は、既存の一次情報・募集/イベント・新着性・手動の関心設定による基本点に、情報源の最大±24点と話題の合計最大±18点を重ねる。確率は `P0` に寄せられるため、1回だけの誤タップは大きな加点・減点にならない。判定が5件に達するまでは既存の順位を維持する。

### 安全性と可視性

- モデルは収集時にSQLiteの直近500件の判定から再構築する。外部のAI/APIへ判定本文、Gmail、Googleカレンダーを送らない。
- 英字の境界を判定し、`email` 内の `AI` のような誤一致を話題として学習しない。
- `/algorithm` では、全体興味確率、α、話題ごとの件数・補正、情報源ごとの確率・信頼度・補正を表示する。画面から履歴を変更することはない。
- X APIの検索語も同じ平滑化で選び、明示的な興味設定を最優先する。検索語は最大6語のままで、監視先や取得量を増やさない。
- `/feed` は未判定の候補を表示するたびに同じモデルで再順位付けする。興味あり・なしを保存すると次のカード順と次回のX収集の両方へ反映される。SQLiteに保存済みの基本スコアは破壊的に書き換えない。

### 検証方針

通常の正負評価、5件未満で不変、強い興味なし、除外語に加え、単発の高評価より複数回の高評価の信頼度と補正が強くなること、候補へ適用した情報源・話題の根拠が返ることをユニットテストで確認する。

## Windowsログイン時のlocalhost自動起動（2026-09-07）

`DailyNews Local Server` というWindowsタスクをログイン時トリガーで登録する。起動スクリプトは最初にTCP 3000番の待受を確認し、既存のDailyNewsや他のサーバーを停止・上書きしない。待受がなければ、保存済みの本番ビルドを `127.0.0.1:3000` で非表示起動する。ビルドが存在しない初回だけローカルでbuildする。タスクはログインユーザーの権限で実行し、外部公開・ネットワーク設定・収集頻度は変更しない。タスク登録が管理ポリシー等で拒否された場合は、同じアカウントの `HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Run` へ起動コマンドを登録してフォールバックする。
