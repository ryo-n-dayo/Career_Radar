# DailyNews 設計・運用記録

最新の画面改善記録: [技術イベントの検索・保存・参加メモ（2026-09-05）](EVENT_DISCOVERY_UX_2026-09-05.md)

更新日: 2026-09-03  
対象: localhost で使う個人用のX新着情報フィード

## 1. 目的

DailyNews は、インターン、採用、説明会、イベントなどにつながる **Xの新着投稿を、毎日自分向けに選び直す** 個人用フィードである。

情報源を一箇所に保存し、以下を可能にする。

- 登録したXアカウントの新着投稿を、公式X APIで取得する。
- 1件ずつ「興味あり」または「興味なし」で判定する。
- 判定履歴から、役に立った語句と情報源を次回の優先順位へ反映する。
- 気になった投稿だけ、Xの元投稿を開いて確認する。

企業台帳、イベント、予定、カレンダーの既存機能は、過去データを壊さないために残すが、日々使う導線には置かない。

対象は個人利用であり、外部公開、ユーザー登録、クラウドDB、ログイン情報の収集は前提にしない。

## 2. 設計方針

### Xフィード優先

日々の主役はX APIで取得する投稿である。企業Webサイトの監視は補助的な収集元として設定画面だけに残す。X APIは利用量上限を守り、公式API以外の取得はしない。

### 速報性と安全性を分離

登録したX API監視先を毎朝5:00に確認する。Cookie保存、ログインの自動化、非公式スクレイピングは使わない。

### 収集した本文を再配布しない

DailyNews は、URL、タイトル、短い要点、判定理由、更新ハッシュを保存する。取得したページ全文を保存・転載・公開する設計にはしない。応募や判断の前には、必ず元ページを開いて確認する。

### 判断は人が行い、学習は補助する

自動処理は候補を並べるだけである。本人が「興味あり」「興味なし」を押し、応募や連絡の判断は必ずXの元投稿を開いて行う。

## 3. 利用フロー

```text
X API監視先を追加
        ↓
毎朝 05:00 に新着投稿を取得
        ↓
優先順位を付けてフィードへ保存
        ↓
09:00頃にフィードで1件ずつ興味あり／なしを判定
        ↓
興味があればXの元投稿を開いて確認
```

X APIを設定していない間は、フィードに新しいX投稿は自動追加されない。練習用サンプルで判定の感覚を試し、APIを設定した後に本番フィードを開始する。

## 4. 画面と機能

| 画面 | 役割 |
|---|---|
| `/` | ホーム。未判定数、監視数、直近の投稿、フィードの成長をまとめて確認する |
| `/feed` | 毎日のXフィード。先頭の投稿を「興味あり／なし」で直感的に判定し、元のX投稿を開く |
| `/internships` | 公式採用ページで現在確認できるIT・エンジニア系インターン募集の一覧 |
| `/sources` | X API監視先、収集実行、希望語・不要語、利用量上限の設定 |
| `/companies`、`/posts`、`/events`、`/admin` | 既存データを保つために残す補助画面。日々のナビゲーションには表示しない |

`/internships` は文章中心の一覧ではなく、会社、技術領域、実務・長期・短期の形式、確認日、技術タグをカードで把握する「Opportunity Board」とする。詳細な説明はカードに詰めず、公式ページを開いて確認する。
| `/terms` | 収集の安全条件と利用上の注意 |
| `/privacy` | 保存データと外部送信の範囲 |

### 画面デザイン

左側のメニューバーは「ホーム」「Xフィード」「インターン募集」「収集設定」の4項目にする。ホームは操作画面ではなく、未判定数・直近の投稿・監視数・学習状況を短く確認する要約画面とする。投稿の判定はXフィードに集約し、1件ずつ「興味あり／興味なし」で進める。

配色は、白に近い暖色の背景、深い茶色の本文、テラコッタの操作色を使う。青系の強い管理画面ではなく、朝に開いても目が疲れにくい読み物のような温度感を目指す。

## 5. 技術構成

| 項目 | 採用技術 | 理由 |
|---|---|---|
| UI / サーバー | Next.js App Router + React | localhostで画面とAPIを一体で扱える |
| 言語 | TypeScript | 収集データ・API・画面の型を揃える |
| DB | SQLite + Prisma | 個人利用で導入が軽く、データをPC内に置ける |
| スタイル | Tailwind CSS | 既存画面の表示を揃えやすい |
| テスト | Vitest | robots判定、優先度判定、既存のイベント取込を検証する |
| 定期実行 | Windows Task Scheduler + PowerShell | サーバー不要で、毎朝5:00に実行できる |

データベースファイルは `prisma/dev.db` であり、Git管理外に置く。

### UIデザイン方針

画面は、Apple Designの「目的・分かりやすさ・控えめな素材感」を参考に、次の順番で情報を置く。

1. ホームでは未判定数、直近の投稿、監視数、学習状況だけを短いカードで示す。
2. Xフィードでは先頭の投稿と「興味あり／興味なし」を最初に表示する。
3. 収集設定では監視先、希望語、利用量上限をまとめ、日常の判断画面からは分ける。
4. カードは大きめの角丸、控えめな影、暖色の背景で階層を作る。装飾よりも、入力・状態・次の行動を優先する。
5. 見出しは詰めた文字間、本文は読みやすい行間と十分な文字サイズにする。動きを減らすOS設定では、アニメーションを最小化する。

## 6. データモデル

### Company

企業台帳。企業名、公式サイト、採用ページ、Xアカウント、業界、メモ、タグを持つ。X投稿、イベント、監視先と紐付く。

### WatchSource

確認する公開情報源。

- `url`: 監視対象URL。重複登録しない。
- `kind`: `PAGE`、`CAREERS`、`RSS`、`SITEMAP`、`X_MANUAL`、`X_API`。`CAREERS` は企業の公式採用ページ、または企業が直接公開したATS上の求人ページ（例: HERP Careers）を低頻度で確認し、技術系インターンの現在募集中状態を更新する。
- `confirmedAt`: 利用条件を人が確認した日時。`PAGE`、`RSS`、`SITEMAP`、`X_API`は未確認のまま自動収集できない。
- `etag`、`lastModified`、`contentHash`: 差分取得に使う。
- `lastExternalId`: X APIで最後に確認した投稿ID。次回はそれより新しい投稿だけを要求する。
- `lastStatus`、`lastError`: 取得状況を画面に示す。

### Candidate

収集により見つかった未確認の候補。

- `url`、`title`、短い`summary`
- `kind`: `INTERNSHIP`、`RECRUIT`、`EVENT`、`COMPANY_UPDATE`
- `score`: 緊急度と関連度の目安（0〜100）
- `reasons`: 例: 「インターン」「締切・先着」「48時間以内」
- `deadline`: 本文から推定できた締切候補
- `status`: `NEW`、`REVIEWED`、`IGNORED`
- `isActive`、`lastSeenAt`: `CAREERS` で直近の確認時にページ上で見つかったかを示す。募集がページから消えても候補データは削除せず、現在募集中の一覧からだけ外す。

### SavedPost / Event

既存のX投稿保存と予定管理を維持する。`SavedPost`と`Event`は任意で`Company`に紐付く。

## 7. 公式サイト収集の仕組み

### 取得前の安全確認

1. URLが `http` または `https` であることを確認する。
2. DNS解決後のIPがローカルネットワーク、ループバック、リンクローカル等ではないことを確認する。これは任意URL取得による内部ネットワークアクセスを防ぐためである。
3. 対象ホストの `robots.txt` を確認する。
4. `DailyNewsBot` に対する最長一致ルールを評価する。
5. 禁止されている、robots.txtを安全に取得できない、利用条件確認がない場合は停止する。

### 取得量の制限

- 1回の本文は最大1MBまで読む。
- リダイレクトは最大5回までとし、各遷移先でも安全確認をする。
- タイムアウトを設定する。
- 更新がない場合は `ETag`、`Last-Modified`、本文ハッシュで処理を省略する。
- ページ全体を横断的に大量巡回しない。登録されたページ、RSS、サイトマップを低頻度で確認する。

### 種類別の抽出

| 種類 | 抽出内容 |
|---|---|
| `PAGE` | タイトル、description、同一ドメインの関連リンク、JSON-LDの`JobPosting`・`Event` |
| `RSS` | item / entryのタイトル、URL、要約、公開日時 |
| `SITEMAP` | 関連URLと最近更新されたURL、`lastmod` |
| `X_MANUAL` | 自動アクセスせず、公式画面を開くための登録だけを行う |
| `CAREERS` | 企業公式採用ページ、または企業が直接公開したATS求人ページのリンク・JSON-LD `JobPosting` から、インターンかつIT・エンジニア・開発・データ・AI・インフラ等の技術職語を持つ募集だけを保存する。営業・セールス・販売・人事・マーケティング等を含むものは保存しない。求人まとめサイト・転載ページを横断巡回しない。 |

`CAREERS` では、採用トップページから見つかった同一ドメインの技術系募集詳細ページを最大8件まで確認する。「応募詳細」のような汎用リンクでも、求人詳細らしいURLに限って本文を確認し、技術系インターンだけを残す。各詳細で取れる場合は、職務説明、雇用形態、勤務地、必要スキル、応募資格、締切を要約へ保存する。ATSを使う場合も、企業名・企業サイトへの導線・直接の応募フォームがある公開求人ページだけを対象にする。各リンクでも公開URL確認とrobots.txt判定を行い、ログイン・CAPTCHA・アクセス制限を伴うページには進まない。

対象ATSは HERP Careers に加え、企業が直接公開する Lever と Greenhouse の求人ページも扱えるようにする。X APIで取得した投稿についても、企業・主催者として確認できた発信元かつ採用・イベント条件を満たし、投稿中の展開済みURLがこれらの公開ATSである場合だけ、候補カードの「元ページ」をその直接求人へ向ける。短縮URLの独自展開、求人まとめサイトへの遷移、未確認URLの自動登録はしない。新しいサイトを収集対象に追加する際は、公開性・利用条件・robots.txtを個別に確認する。

### 技術イベント発見

左メニューの「技術イベント」は、インターン募集と並ぶDailyNewsの主機能である。ハッカソン、技術体験、開発者向けミートアップ、勉強会、ワークショップ、Tech Talk、デモ体験、技術者交流を対象にする。採用Meet Upはその中でエンジニアと交流できるものだけを残す一カテゴリであり、専用収集にはしない。

X APIの検索結果のうち、企業・団体の公式発信または信頼できる主催者の一次告知であり、以下を同時に満たすものだけを表示する。

- 技術領域：エンジニア、開発、プログラミング、ソフトウェア、AI・LLM、データ、クラウド、セキュリティ、デザイン、プロダクト等。
- 参加形式：ハッカソン、ミートアップ、勉強会、ワークショップ、技術・デモ体験、説明会、座談会等。
- 実際の参加告知：開催、参加者募集、申込み、受付、予約、参加可能等。

一般的な催事、登壇だけの告知、スポンサー投稿、求人装飾・グッズ紹介、参加者の感想は除外する。収集は1日最大20投稿とし、企業の新着10投稿と合わせてX APIの日次30投稿上限を超えない。投稿カードは、分かる範囲で日程・会場を抽出し、必ず元の公式告知または申込ページを開く導線を残す。

Xの技術イベント探索では、日本語に加えて英語の `hackathon`、`meetup`、`workshop`、`conference`、`summit`、`hands-on` と、`registration` 等の参加告知を検索する。海外の投稿を対象に広げても、企業・団体または技術コミュニティの主催者であり、公式サイト・組織プロフィール・認証などの根拠を持つ一次発信だけを残す。個人の参加感想は除外する。

### 候補の優先度

キーワードと期限をルールベースで評価する。最初は外部AIを使わない。

- 「インターン」: 高優先
- 「採用」「募集」「エントリー」「選考」: 採用候補
- 「説明会」「イベント」「登壇」「交流会」: イベント候補
- 「締切」「先着」「本日中」「追加募集」: 緊急度を加算
- 締切まで48時間以内: 大きく加点
- 掲載から24時間以内: 加点

この点数は判断の代替ではない。誤検出や締切推定の誤りがあり得るため、元ページ確認を必須にする。

## 8. Xの方針

Xは「投稿が短時間で流れる」という用途に重要だが、無料で安定した自動取得を前提にしない。

- Xのログイン情報、Cookie、パスワードは保存しない。
- 非公式RSS、ログイン済みブラウザの自動操作、アクセス制限の回避は実装しない。
- 個別アカウントの固定監視は補助機能とし、日々の主役にはしない。
- 「今すぐ収集」は、興味あり／なしの履歴と希望語から公式X APIの検索語を選び、個人向けの検索フィードを作る。
- 自動フィードでは、一般ユーザーの感想・体験談を候補にせず、企業・団体の一次発信だけを採用する。
- 有料のX APIは、日次・月次の上限内だけで使う。

### X APIを有効化した場合の上限

個別のアカウント監視は `X_API`、自動で作る個人向け検索フィードは `X_ALGO` として保存する。APIキーはSQLiteや画面には保存せず、PC内の`.env.local`だけに保存する。

```dotenv
X_API_ENABLED="true"
X_API_BEARER_TOKEN="Developer Consoleで発行したBearer Token"
X_API_DAILY_POST_LIMIT="30"
X_API_MONTHLY_BUDGET_USD="5"
X_API_KEYWORDS="インターン,採用,募集,説明会,イベント,エントリー"
```

実装上の制限は次の通り。

- 通常の投稿取得を `$0.005/投稿` として概算する。
- SQLiteの`XUsageDaily`に日ごとの投稿数・リクエスト数・概算費用を保存する。
- 1日の投稿上限、月間概算上限のいずれかに達したら、その日は自動取得を停止する。
- 企業の新着フィードと学生向けイベント発見フィードを分け、各フィードで1回あたり最大10投稿を取得する。通常の自動収集では最大20投稿／日とし、30投稿の上限を超えない。
- `since_id`を保存し、前回より新しい投稿だけを要求する。
- 個別監視のクエリは `from:アカウント` と必要語句を組み合わせる。自動フィードは、興味ありの投稿に多い語句と希望語を最大6語選び、企業の採用・事業更新用と、学生・インターン・キャリアを軸にしたイベント発見用を別々に検索する。イベント発見用には、希望語が少ない初期段階でも `エンジニア`、`開発`、`デザイン`、`デザイナー`、`プロダクト`、`UI/UX`、`AI` を探索語として加える。いずれもリポストと返信を除外して横断検索する。

Developer Consoleでも月間のSpending limitを同じく`$5`に設定する。アプリ側の上限は安全弁であり、X側の上限設定も必須と考える。

有効化の手順は以下とする。

1. X Developer Consoleでアプリを作成し、料金上限を設定する。
2. Bearer TokenをPCの`.env.local`にだけ保存する。チャット、画面、SQLite、Gitには貼り付けない。
3. `X_API_ENABLED="true"`に変更する。
4. `/sources`で「今すぐ収集」を押す。初回は`X_ALGO`の個人向けフィードが自動作成され、同時に収集する。
5. 以後は興味度の履歴を使って検索語を更新し、翌朝05:00にも実行する。画面の利用量表示が上限内であることを確認する。

トークン未設定・`X_API_ENABLED`が`false`・上限到達のいずれの場合も、X APIへの取得リクエストは行わず、画面に理由を表示する。

### フィードバック学習

候補に対する5段階の興味度を学習データにする。単に閲覧しただけの候補は学習しない。

| 興味度 | 数値 | 扱い |
|---|---:|---|
| 最優先 | +2 | 強く加点する学習例 |
| 興味あり | +1 | 加点する学習例 |
| 保留 | 0 | 表示からは外すが、学習には影響させない |
| やや違う | -1 | 減点する学習例 |
| 興味なし | -2 | 強く減点する学習例 |

### 初回の好み合わせ（練習用サンプル）

「自分向けに絞り込む」の **練習用10件を追加** は、外部通信・X API料金を使わずに、架空の候補10件をSQLiteへ追加する機能です。各候補はタイトルに「【練習用】」と明記し、元ページへのリンクも表示しません。実在する企業、求人、イベントとして扱わないでください。

初回は10件それぞれに「興味なし」から「最優先」までの5段階を付けます。評価は検索語と候補の優先順位を調整するために使われ、練習用の監視元そのものは自動巡回の対象にしません。既に追加したサンプルを再度追加しても、既存の評価は上書きしません。

1. 既存のキーワード・鮮度・締切スコアを基礎点にする。
2. 過去の興味度の平均から、情報源ごとに加点・減点する。
3. 過去に役立った／不要だった語句を補正に使う。
4. 最終スコアとともに「この情報源の保存実績」「過去に役立った語句」など理由を画面に残す。

この学習はSQLite内だけで行い、外部AIへ候補本文を送らない。判定例が5件未満の間は学習補正をせず、ルールベースのスコアをそのまま使う。

### 企業情報に絞るための投稿者・投稿フィルター

個人向けの `X_ALGO` フィードでは、検索語に一致しただけでは保存しない。公式X APIの `author_id` 展開で同時に得られる投稿者プロフィールを使い、次の二段階を通った投稿だけを候補にする。

1. **企業・団体らしい投稿者**: 自己紹介・表示名・アカウント名に「公式」「採用」「株式会社」等の組織を示す語がある、または公式サイトURLと認証状態／一定の公開フォロワー数の組合せがあることを確認する。認証バッジやフォロワー数だけでは採用しない。
2. **一次性のある告知**: 採用、募集、インターン、説明会、リリース、資金調達、新規事業、プレスリリース、公式イベント等の語があることを確認する。一般ユーザーの「参加してきた」「感想」「最高」等の体験談は除外する。
3. **隠れイベントの発見**: 企業名で発信していない場合でも、スタートアップ・採用・学生キャリア・VC・コミュニティ等を専門にし、認証、公式サイトURL、または十分な公開フォロワー数のいずれかを持つ主催／共催者の告知は候補にする。「学生向け」「キャリアイベント」「参加者募集」「主催・共催」などが本文にあることを追加条件とし、一般参加者の感想とは区別する。企業公式による学生参加可のエンジニア・デザイン・プロダクトイベントも同じ一次情報として対象にする。

これはXの非公開の推薦アルゴリズムを再現するものではない。公開APIで取得できる投稿者情報、鮮度、話題一致、本人の評価履歴を使う、説明可能なローカル順位付けである。投稿者情報は `expansions=author_id` と `user.fields` で `includes.users` に含められるというX APIの公開仕様に基づく。Xの公式ドキュメント: [Expansions](https://docs.x.com/x-api/fundamentals/expansions)、[Recent Search Quickstart](https://docs.x.com/x-api/posts/search/quickstart/recent-search)、[User Lookup Quickstart](https://docs.x.com/x-api/users/lookup/quickstart/user-lookup)。

この変更後も、過去に保存済みの候補は削除しない。ただし、企業一次情報フィルター導入前の `X_ALGO` 候補はフィードから隠す。企業・イベント一次情報フィルターの更新直後の最初の手動収集は最新範囲を取り直し、好みのトピックを変更した場合も `since_id` をリセットして新しい検索条件で取得し直せる。自動フィードがある状態の「今すぐ収集」は、常にこの個人向け検索条件を更新してから実行する。

### 個人用の収集条件

`InterestProfile` に、ユーザーが画面で入力した「欲しい情報」と「不要な情報」をSQLite内だけに保存する。

- 事前に選ぶ小さなトピックチップ（AI・生成AI、長期インターン、学生向けキャリアイベント、デザイン・プロダクト、スタートアップ、海外・東南アジア、データ・エンジニア、事業開発、VC・投資、イベント・コミュニティ、教育）は最大6つまで保存する。
- トピックを「選択を保存」した時点の組合せと時刻は、直近20回分をSQLite内の選択履歴として残す。現在の選択を変更しても、過去の関心の推移を収集設定画面で確認できる。
- トピックは検索語へ展開し、手入力の希望語より強い優先条件として候補の順位にも使う。
- 選択されたトピックに一致しない候補は減点する。これにより、初期の汎用的なX検索結果を減らす。
- 欲しい情報に一致する候補は加点する。X APIでは、企業アカウント・募集関連語に加えて、希望語も検索条件にする。
- 不要な情報に一致する候補は大きく減点する。取得そのものを隠さず、候補の理由として除外条件を表示する。
- 希望語があるのに一致しない候補は、小さく減点する。完全に捨てず、締切など重要な情報を見落とさない。
- 「役立った」「不要」の評価履歴による学習と併用する。設定・評価履歴は外部AIへ送信しない。

## 10. 法律・利用条件の前提

これは法的助言ではない。サイトごとの利用規約、対象国、取得内容、頻度、利用目的によって評価が変わるため、疑義があるサイトは登録しない。

### 実装上の保守的な条件

- 「個人利用だから自由」とは扱わない。
- 各サイトの利用規約を確認し、自動取得の禁止がある場合は登録しない。
- `robots.txt`の`Disallow`を尊重する。
- 認証・有料壁・CAPTCHA・技術的制限・ログインを迂回しない。
- 公式サイト、公式RSS、公式サイトマップを優先する。
- 原文の大量複製、再配布、第三者への公開をしない。
- 連絡先等の個人情報を不必要に蓄積・照合しない。

### 参照資料

- [著作権法（e-Gov）](https://laws.e-gov.go.jp/law/345AC0000000048) — 第30条の4は情報解析等に関する規定を含むが、権利者の利益を不当に害する場合は除外する。
- [不正アクセス行為の禁止等に関する法律（e-Gov）](https://laws.e-gov.go.jp/law/411AC0000000128) — アクセス制御を不正に回避する行為を禁止する。
- [個人情報保護委員会FAQ](https://www.ppc.go.jp/all_faq_index/faq1-q1-5/) — 公開済みの情報でも、取扱いによっては個人の権利利益を害し得る。
- [RFC 9309: Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html) — robots.txtの標準仕様。
- [Sitemaps protocol](https://www.sitemaps.org/protocol.html) — `lastmod`を使った差分確認の仕様。
- [Google Search Central: JobPosting](https://developers.google.com/search/docs/appearance/structured-data/job-posting) — 公式採用ページの構造化データから、職種・掲載日・有効期限などを抽出できる場合がある。

`robots.txt`は法律上の許諾を単独で判断するものではない。DailyNewsでは、技術的・運用上の最低限の安全条件として尊重する。

## 11. プライバシーと外部送信

- 主要データはPC内のSQLiteに保存する。
- 公式Webサイトの監視時は、そのサイトに通常のHTTPリクエストを送る。
- `OPENAI_API_KEY`を設定してAI要約を使う場合のみ、要約対象のX投稿本文がOpenAI APIへ送られる。未設定なら送信しない。
- Xの認証情報は保存しない。

### Gmail・Google Calendar連携

- Googleの公式OAuth 2.0（Authorization Code + PKCE）を使う。「Googleでログインして連携」を1回押すと、同じGoogle同意画面で本人確認とデータ読み取り許可をまとめて行う。
- 要求する権限は本人確認用の `openid`、`email`、`profile` と、読み取り専用の `gmail.readonly`、`calendar.readonly` のみ。メール送信、削除、予定の作成・変更はしない。
- Gmail本文・添付・参加者リストは保存しない。保存対象は差出人、件名、短いスニペット、受信日時、Gmailを開くURLだけである。画面に表示するのは、インターン関連、または技術領域を伴うイベント（ハッカソン、開発者向けセミナー、技術カンファレンス等）のメールに限定する。単なる技術ニュース、請求、一般の予定通知は表示しない。
- Calendarは予定名、開始・終了日時、場所、Google Calendarの元予定URLだけを保存する。説明文は保存しない。
- OAuthトークンは `GOOGLE_TOKEN_ENCRYPTION_KEY` でAES-256-GCM暗号化してSQLiteに保存する。キーは `.env.local` のみに置く。連携解除時はトークンと同期済みデータをSQLiteから削除する。

#### 初回のOAuth設定

1. Google Cloud Consoleでプロジェクトを作成し、Gmail APIとGoogle Calendar APIを有効にする。
2. OAuth同意画面を設定し、テスト中は自分のGoogleアカウントをテストユーザーに加える。
3. OAuthクライアントは「Web application」で作成し、承認済みリダイレクトURIに `http://localhost:3000/api/google/callback` を登録する。
4. `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`、32バイトの `GOOGLE_TOKEN_ENCRYPTION_KEY` を `.env.local` に保存してから、DailyNewsを再起動する。

Googleログインだけ（`openid`、`email`、`profile`のみ）ではGmail・Calendarの内容は取得できない。DailyNewsでは、最初の1回の同意画面に必要な読み取り専用権限もまとめて表示し、許可後に初回同期まで自動で実行する。

### 技術イベントの個人向け条件（2026-09-04更新）

技術イベントは、通常のXフィード用の興味条件とは別に、`InterestProfile` 内のイベント専用項目としてPC内のSQLiteへ保存する。

- 分野は AI・LLM、クラウド、ハッカソン、データ、デザイン、OSS・セキュリティ、交流会・実践から複数選べる。
- 「交流したい人」と「聞きたい話」は、カンマか改行で入力する。例: `AIエンジニア, 起業家`、`アイデア創出, LLM実装`。
- 一致する候補には「あなた向け」の理由を表示して先頭に並べる。必要なときだけ一致候補に絞り込める。候補が不足している段階では、不一致の候補も消さずに表示する。
- 保存後、次の公式サイト収集とXの技術イベント探索にだけ条件を反映する。企業の通常フィード、メール、カレンダーには影響しない。
- `Design Sprint`、`デザインスプリント`、`アイデアソン`も、技術・プロダクトの実践イベントとして検出対象に含める。

### connpass の扱い

connpassはIT勉強会・イベント向けの公式サービスだが、通常ページの自動クローリング・スクレイピングは利用規約で禁止されている。DailyNewsはconnpassの通常ページを自動取得しない。公式APIはAPIキーが必要で、個人・コミュニティ利用は利用申請・審査後に無償で1キーが発行される案内である。APIキーの設定を希望する場合だけ、公式API用の接続として別途追加する。
